# 维护与来源：通用规则怎样持续更新

本仓库提供独立的通用整理稿和本地工具。来源实例的规范在HiveOS维护，通用稿按采用项目的实际范围确认；公共贡献可以改进说明、模板、示例和工具，不需要获得私有来源仓库的访问权。

## 1.先找到负责的位置

- 长期规则放在九项STD中，每项事实只完整维护一次。
- 入门说明、协作指南与工具说明面向使用者，解释规则与命令，不另增业务授权。
- 模板是草稿，不是假定已经发生的任务或验收。
- 来源清单保存原文件路径、原始SHA-256、目标及删改；新增工具注明由本仓库创建。

官网是连续介绍，本仓库是可下载与改编的规范、模板和工具。ACDL与来源项目的完整维护顺序为规范→介绍→网站→独立仓库；本仓库的通用稿不复制来源业务、环境与个人配置。

## 2.怎样核对来源更新

维护者具备既有HiveOS访问权限时，选择规范与介绍一致的完整提交，用`git show`读取原始字节，逐文件比较原始摘要与实际改动。不能只换清单中的日期和SHA就宣称内容已经同步。

先判断变化属于通用方法、来源专用事实还是本仓库工具能力：

1. 通用规则的变化，保留含义并更新STD、指南、模板和受影响测试。
2. 来源项目的环境授权、业务状态、真实台账和本机目录，不复制到通用项目。
3. 本仓库独有的示例与工具，记录自身变更与验证，不声称上游有同名实现。
4. 调整文件名时同步本地链接与来源清单的目标路径，不保留两份相同正文。

原始摘要始终对应所选来源文件的原始字节，不能用整理稿的摘要替换。来源HiveOS仍为私有，本仓库已按Apache-2.0公开；公共读者可以直接使用这里发布的材料，来源访问不是离线试用的前置条件。

## 3.检查、贡献与公开范围

运行README中的检查、测试和示例，说明失败、未运行与未验证范围。默认CI只在合成数据上验证Node.js22和24，没有账号、数据库、部署或来源仓库访问步骤。

每次公开更新还应审阅新提交及GitHub讨论、日志、附件和制品。常见模式扫描不保证发现全部秘密，发现实际敏感内容后先私密核验影响。许可、贡献与报告方式分别见[LICENSE](../LICENSE)、[贡献说明](../CONTRIBUTING.md)与[安全说明](../SECURITY.md)。
