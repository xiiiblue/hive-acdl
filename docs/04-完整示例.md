# 完整示例：从需求到可核对的验证

这是一条“导出只返回当前用户记录”的合成教学链路，不连接数据库、账号或真实服务，也不声称完成生产导出功能。它展示ACDL怎样把一条需求、设计约束和测试对应起来。

## 1.运行

在仓库根目录执行：

```sh
npm run demo
```

输出中的`.tmp/acdl-demo-*`是本次生成的独立目录。根仓库的需求登记与追踪账本仍为空白；示例内容只在新目录中。可再次运行产生另一份目录，旧结果不会被覆盖。

## 2.沿着这些文件阅读

|文件|保存什么|
|---|---|
|`docs/01-需求/REQ-000001-合成导出示例.md`|希望导出的结果满足什么条件，明确只是教学范围|
|`docs/01-需求/README.md`|登记示例REQ身份，供追踪引用|
|`docs/02-设计/01-系统设计/SYS-001-合成导出示例.md`|稳定要求SEC-001的完整定义|
|`src/export-demo.mjs`|只筛选当前示例用户的纯函数|
|`tests/export-demo.test.mjs`|混合用户记录的正向检查，以及其他用户记录不应出现的断言|
|`tests/traceability/design-requirements.json`|需求来源、定义摘要、主题和直接验证位置|
|`docs/02-设计/00-索引与追踪/IDX-002-设计要求与验证追踪.md`|由JSON生成的人类阅读视图|

脚本依次生成文件、运行示例测试、生成追踪视图，再运行本地文档与追踪检查。示例里没有Git提交、PR、部署、正式版本或已经结束的Loop，因此也不会伪造相应记录。

## 3.它验证了什么

示例测试给纯函数输入两位合成用户的混合记录，断言结果只含目标用户记录。追踪检查再判断定义摘要、REQ登记、主题与测试标记能否对应。它们分别验证功能断言与记录关系，不能互相替代。

想观察失败，可在**生成目录**中把示例函数改成返回所有记录，然后只运行该测试：

```sh
node --test tests/export-demo.test.mjs
```

测试应失败。若改变设计定义但不更新摘要，`npm run trace:check`也应拒绝。先审查含义、修正实现或定义，再重新运行相关验证；不要为了消除报错直接刷新摘要。

## 4.怎样接到真实项目

真实需求需要补业务对象、权限、输入范围、失败处理和验收，而不仅是改一个筛选函数。示例没有证明API认证、数据库过滤、分页、并发、安全隔离或业务部署。

采用时保留自己项目的事实与编号，从最高受影响的设计开始，再选择需要的实现、真实使用和独立评审。按[快速开始](01-快速开始.md)逐步接入，按[工具与命令](03-工具与命令.md)核对实际写入范围。
