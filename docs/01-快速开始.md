# 快速开始：先用最少的部分

官网的[完整方法手册](https://www.bluexiii.com/acdl/)按场景解释ACDL。本页帮助你在本机运行工具，或在自己的项目中选用一部分材料，不要求先搭建蜂巢或连接任何外部服务。

## 1.确认工具，再运行检查

需要Node.js22+和Git，没有第三方npm依赖。克隆后在仓库根目录运行：

```sh
node --version
npm run check
npm test
npm run demo
```

macOS先运行`export TMPDIR=/tmp`。检查成功只证明本仓库和合成用例，真实业务环境要使用自己的测试与验收方式。

`demo`会输出新目录和已执行检查。打开那个目录，看需求登记、设计定义、示例函数、测试和追踪JSON怎样互相对应。每次运行创建新目录，不清空旧目录；不再需要时，由你删除自己确认的`.tmp/acdl-demo-*`目录。

## 2.只采用一份任务或交接模板

小修改可以直接写清目标、范围、验收和已有差异，再让Agent实施。需要交接时，从[HANDOFF模板](../templates/HANDOFF.md)选用实际需要的字段。

需要持续追踪的一轮工作，再使用[ACL模板](../templates/ACL.md)。不要为了使用模板而虚构REQ、设计、版本或“已经通过”的证据。示例编号是占位，正式编号从采用项目登记表分配。

## 3.逐步接入已有项目

先在自己的分支或隔离目录试用，并检查已有文件：

1. 保留现有AGENTS与权限规则，对照[Agent入口模板](../templates/AGENTS.md)补实际缺口，不覆盖已有授权边界。
2. 选择需要的STD与模板。Review是供采用者确认的通用整理稿，命令、目录、主分支与环境都按自己的项目填写。
3. 想使用追踪工具时，复制适用的`scripts/`、空白`tests/traceability/`及追踪Markdown骨架。先在临时目录建立一条非空合成要求并检查，再接入真实项目。
4. 把需要的命令加入目标项目的package.json，核对脚本从哪里确定项目根目录；不要让它读写原克隆或其他项目。
5. 运行目标项目自己的测试与必要评审，记录采用内容和未接入能力。重新分发时保留LICENSE、NOTICE及适用的来源声明。

直接复制整仓会带入空白登记骨架、贡献说明和教学测试。应按需要选择，逐项检查路径冲突和既有规则，而不是把模板当成安装器。

## 4.从第一条稳定要求开始

稳定要求用于需要长期引用和持续验证的约束，普通文案或单次尺寸调整不用编号。示例格式：

```text
**SEC-001**：导出结果只包含当前用户可见的记录。
```

把定义放在负责该规则的设计中；追踪JSON记录它来自哪里、定义摘要、主题和直接验证位置。测试文件使用`TRACE-REQ`和`TRACE-TOPIC`标记关联。先确认测试真正判断规则，再运行`trace:check`；自动补标记不能代替验证。

完整过程见[可运行示例](04-完整示例.md)。

## 5.选哪一条工作路径

- 已有设计下的低风险修正：实现、相关检查、报告。
- 新能力或重要长期变化：补必要REQ与设计，再实施和验证。
- 固定候选的真实使用：按需开展DFL；独立工程审阅按需开展ERL。
- 正式交付：确认实际范围、证据与剩余问题；环境更新和正式版本分别核验。

详细规则见[协作指南](02-协作指南.md)。下一次换Agent时，交接当前事实与完整提交，不让新会话猜历史决定。
