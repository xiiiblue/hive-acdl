# STD-001：ACDL文档治理规则

> 文档状态：Review
>
> 提取说明：由来源规范整理为通用草案；项目命令和目录按采用项目配置。
>
> 责任角色：Director
>
> 本文负责：`docs/`中的内容归属、文档状态、文件命名、稳定编号、历史材料和维护规则

## 1.一项事实只在一个位置完整维护

|内容|负责位置|
|---|---|
|长期工程规则|`00-规范/`|
|REQ和候选路线|`01-需求/`|
|当前设计、ADR和设计追踪|`02-设计/`|
|Issue身份、状态和处理去向|`03-实施/ISSUE/`|
|Issue处理、ACL、DFL、ERL及证据|`03-实施/`|
|正式版本范围、验收和发布说明|`04-版本/`|
|当前环境状态和变更记录|`05-环境/`|
|手册、交流和交付说明|`11-手册/`至`13-交付与申报材料/`|
|退出当前入口的历史事实|`21-历史工作记录/`和`22-历史基线材料/`|

其它文档只概括并链接。发生冲突时修正不负责该事实的位置，不能简单选择更新或更详细的一份。计划保存准备做什么，记录保存实际发生什么；结果不能反写成原计划，一次实施也不能冒充所有环境或正式版本已经具备。

## 2.文档状态

|状态|含义|
|---|---|
|`Draft`|仍在整理，内容可能不完整|
|`Proposed`|已经可以评审，等待决定|
|`Review`|正在评审，实质内容仍可能变化|
|`Accepted`|Director已经确认，当前可以作为依据|
|`Completed`|计划、记录、活动或版本对应的工作已经结束|
|`Withdrawn`|尚未确认的方案或计划停止|
|`Superseded`|曾经有效，已经被其它文档或决定替代|
|`Rejected`|ADR经过评审后明确不采用|

`Rejected`只用于ADR。正式规则和当前设计通常使用`Accepted`，已经结束的Loop和版本使用`Completed`，持续变化的环境状态使用`Review`。

1. 错字、排版、链接或不改变含义的表达修改保留原状态；移动和改名本身也不改变状态。
2. 准备改变Accepted的重要长期结论时先转为`Review`，只重新确认变化部分。已授权范围内的局部表达、表现细节和实现说明按STD-003处理，不因正文有变化就重新申请确认。
3. `Proposed`和`Review`处理完阻塞问题后才能进入终态；正式规则和设计进入`Accepted`必须有Director确认，Loop按[STD-008](STD-008-实施流程规范.md)记录结束依据。
4. 被替代的文档标记为`Superseded`，新旧入口互相链接。
5. 状态变化和依据写入负责该事实的文档及登记表，不能只留在聊天中。

新稿处于`Review`时，上一份`Accepted`提交或标签继续有效。修订稿必须注明仍有效的完整提交或标签、文件路径和本次变化范围，让读者能直接找到当前依据；只重审变化部分，不把未改变的要求视为失效。隔离原型通过也不自动成为正式设计。

## 3.文件和编号

目录索引统一使用`README.md`。主要文件名如下：

|对象|格式|
|---|---|
|规范|`STD-三位编号-标题.md`|
|需求|`REQ-六位编号-需求简称.md`|
|系统设计|`SYS-三位编号-标题.md`|
|能力设计|`CAP-三位编号-标题.md`|
|横切设计|`CRS-三位编号-标题.md`|
|决策记录|`ADR-四位编号-决定名称.md`|
|索引和追踪|`IDX-三位编号-标题.md`|
|Issue详情|`ISSUE-六位编号-问题简称.md`|
|交流材料目录|`YYYYMMDD-活动简称/`|
|当前环境|`<环境名>环境.md`|
|环境变更记录|`变更记录/<环境名>环境变更记录.md`|
|项目验收和客户交付|`ACCEPT-三位编号`|
|正式版本镜像发布物清单|`V<主版本>.<次版本>-发布物清单.md`|
|软件著作权|`COPYRIGHT-三位编号`|
|专利|`PATENT-三位编号`|

能力设计默认平铺。只有同一能力确实需要两份以上长期独立维护的设计时才建立同名目录，并保留`CAP-xxx-能力名称.md`作为主设计。

编号一经使用不修改、不回收、不复用。标题可以调整；旧编号迁移登记到`IDX-003`，不复制相同正文兼容旧路径。

当前产品、设计和规范至少写明状态、责任角色（统一为Director）及负责范围；ADR、计划和记录按用途补充日期、依据、对象和证据。

## 4.稳定设计要求和验证追踪

需要长期引用和持续验证的规则才分配稳定设计要求编号，包括用户承诺、权限、安全和数据规则，以及跨模块、接口、迁移、部署和恢复约束。单页布局、尺寸、文案等表现细节在本次验收中说明，不为便于引用而单独编号。

|前缀|用于|
|---|---|
|`PRD-`|平台范围、用户承诺、核心规则和结果指标|
|`DOM-`|领域行为、用户流程、对象生命周期和验收结果|
|`ARCH-`|进程、数据、接口、状态、部署、迁移和恢复|
|`SEC-`|身份、凭据、隔离、网络、审计和数据安全|

每类使用三位编号。同一对象的同一约束修订或移动时保留编号，用Git提交追溯旧含义；约束拆分、合并或改为约束另一对象时才分配新编号并说明替代关系。内容变化后重新核对验证方法，不能只刷新摘要就认为新增行为已经验证。完整定义只写在负责它的SYS、CAP或CRS中：

```text
**SEC-001**：这里写完整规则。
```

其它位置只引用编号并给出必要摘要。设计要求和验证关系保存在`tests/traceability/design-requirements.json`；新增、移动或实质修改稳定要求时更新数据并运行：

```bash
npm run trace:render
```

验证方法使用`test`、`inspection`、`analysis`或`demonstration`；`direct`表示直接判断要求，`supporting`只提供相关证据。追踪文件不保存REQ、Issue、Loop、版本状态或最近测试结果。

## 5.移动、拆分、合并和删除

移动或改名时检查链接、索引、追踪数据、脚本和历史入口。旧路径默认通过Git历史、标签和`IDX-003`追溯；仓库外存在无法同步的依赖时，可以保留说明用途和移除条件的临时跳转页，不复制正文。是否需要确认按根`AGENTS.md`判断。

文档混合不同职责、当前结论与历史过程，或面向不同读者时可以拆分；职责和维护方式相同时才合并。结构调整不得改变已确认结论。

删除前确认文档没有保存唯一的产品或设计要求、批准记录、实施或测试证据、环境恢复入口、外部交付依据。能够通过`Superseded`、历史目录或简短说明追溯时，不直接删除。

图片、HTML和演示文件也要有入口并接受敏感信息检查；重新生成时不覆盖历史证据、失败候选或已交付版本。

## 6.历史材料

`21-历史工作记录/`保存退出日常入口的旧工作记录；`22-历史基线材料/`保存已被当前产品整体替代的旧基线。仍用于当前实现、恢复或问题追踪的记录继续留在原目录。

历史正文保留当时说法，不按现行规则补造编号、状态、REQ、Loop或证据。可以修复路径和格式、补充替代说明；安全、隐私、法律或合规要求删除的敏感内容除外。


## 7.例外

确认边界统一按根`AGENTS.md`判断。一次性、容易恢复且不改变长期产品、安全和证据要求的文档例外，由Agent判断并在现有记录中说明原因、影响和结束条件，不另建审批材料。重要长期例外按STD-003决定是否使用ADR。

例外不能用于删除历史证据、降低Secret保护或绕过已确认的产品、架构和安全决定。移动文档影响代码、部署、测试或验证入口时，运行对应定点检查。
