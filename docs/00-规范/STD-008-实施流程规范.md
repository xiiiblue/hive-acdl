# STD-008：ACDL实施流程规范

> 文档状态：Review
>
> 提取说明：由来源规范整理为通用草案；项目命令和目录按采用项目配置。
>
> 责任角色：Director
>
> 本文负责：规定ACL、DFL和ERL怎样选择、登记、执行、保存证据和结束

|类型|用途|
|---|---|
|ACL（Agentic Coding Loop）|修改代码、测试、脚本、部署定义或正式文档，并完成自动化验证|
|DFL（Developer Feedback Loop）|Director以真实角色使用固定候选并记录反馈|
|ERL（Engineering Review Loop）|针对固定代码、差异或版本开展独立工程评审|

三类Loop可以独立或穿插开展，不是必须依次经过的阶段。DFL和ERL按风险选择，不是每项变化的机械门禁。

本规范说明采用项目应满足的流程合同；本仓库仅提供模板和纯函数，不提供自动Review/Completed命令。工具能力见[工具说明](../tools.md)。

## 1.什么时候建立Loop

命中以下任一条件才登记Loop：

1. 多个独立工作单元需要持续追踪范围、依赖和处理去向；
2. 需要长期保存重要候选的评审、环境操作或恢复证据；
3. 需要记录重要产品取舍、正式决定、遗留风险或正式版本依据。

普通维护、单页表现调整和局部重构直接修改、检查并报告，不强制登记ACL。换会话或换执行者只需保存起点、已有差异、剩余问题和下一步，可使用现有PR或简短摘要，不因换会话升级流程。重要产品变化先按需求与设计规范确定范围；实际需要长期实施记录时再建立ACL。

DFL固定真实环境、制品、提交、角色和账号；ERL固定提交、差异范围或Git标签。两者都只检查固定对象，需要修改时由ACL承接。大型目标按能够独立理解、验证和回退的范围拆分，连续且不能独立验证的步骤保持同一轮。

## 2.身份、版本关系和状态

现行编号使用：

- ACL：`ACL-六位编号`；
- DFL：`DFL-六位编号`；
- ERL：`ERL-六位编号`。

编号只表达身份，不回收、不复用。ACL的计划版本和实际纳入版本使用独立字段，排期变化不改编号；目标、范围或完成条件实质变化到原记录已经无法清楚表达时，才建立新ACL。

|状态|含义|
|---|---|
|`Ready`|范围和启动内容已经准备好，尚未发生第一次真实执行|
|`In Progress`|已经开始编码、实机操作或正式评审|
|`Review`|候选、证据和剩余问题已经整理，等待合入、验收或决定；失败检查如实保留|
|`Completed`|结束依据已记录；ACL还必须已经合入目标分支并记录实际纳入提交|
|`Withdrawn`|本轮停止，原因和已经发生的事实得到保留|

结果与状态分开记录，`Completed`不表示没有问题。结束依据只有两种：

- `verified`：客观完成条件和规定验证通过，没有需要新确认的遗留风险，执行者事后记录；
- `director`：需要新的产品取舍、正式决定、主观验收或风险接受，或接受本次必需检查仍被跳过、未执行或失败时，记录Director确认。

按规定不适用的检查，以及已经修复并通过规定复验的历史失败，不阻止使用`verified`，但必须如实记录；不能将缺少必需验证解释为不适用。

## 3.启动方案和记录

每轮ACL、DFL和ERL只建立一篇主记录，保存目标与范围、当前摘要、重要过程、验证、遗留问题和结论。新ACL只维护一个轮次状态，登记表由状态工具同步；不再另设相同含义的文档状态或独立计划。起点、候选、验证、时间和纳入提交由工具维护，正文不复制整份摘要。

需要在执行前确认的高风险操作、恢复办法或评审范围，写入主记录的启动方案，并在第一次真实执行前取得必要确认。第一次真实执行后，启动方案成为快照；后续变化追加原因和影响，不把结果反写成原计划。


## 4.ACL怎样开展 {#acl-flow}

1. 核对来源、起点、设计依据、计划版本、范围和已有工作树；
2. 完成实现和离修改最近的定点测试；
3. 按[开发验证规范](STD-007-开发验证规范.md)运行统一验证，记录失败、跳过和未验证事实；
4. 工具按启动基线核对整轮变化、档位和证据后进入`Review`；失败候选显式使用`--allow-failed`并说明待决定问题；
5. 满足对应结束条件后合入目标分支；
6. 记录实际纳入提交、结束依据和结论，再进入`Completed`。

一个ACL可以处理多个同根因或同验证路径的问题，不强制“一Issue一ACL”。

结束依据看是否仍有需要人作出的决定，不按“发布”“数据”等任务名称机械选择。目标和操作已经授权、客观完成条件及必需检查通过且没有需要新确认的遗留风险时，可以使用`verified`；新的正式决定、主观验收或风险接受使用`director`并引用已取得的确认。既有授权不再重复申请。进入Review允许失败证据，使用`verified`结束仍必须有覆盖整轮变化的成功证据。

## 5.DFL怎样开展 {#dfl-flow}

DFL围绕一个角色、真实任务或待决定问题开展。开始前固定环境、制品、提交、角色和账号；每次候选变化都开始新的Attempt。

DFL只记录真实操作和发现，不修改被测对象。需要修改时保留局部Finding，由ACL承接；需要跨工作单元追踪时再建立全局Issue。修复后固定新候选并开始下一Attempt。

DFL客观结果依据操作、数据和审计证据记录，不重复确认证据。主观体验与未完成范围需要新的取舍时由Director决定；按规定不适用或已经授权的低风险事项直接记录，不重复确认。

## 6.ERL怎样开展 {#erl-flow}

ERL针对固定提交、差异范围或标签独立检查。未经复核的推测不能登记为确认问题；修复由ACL承接，原ERL保留固定基线上的发现。

## 7.发现、证据和版本

DFL、ERL先使用本轮局部Finding编号；需要跨工作单元、责任人或版本继续处理时才建立全局Issue。Issue、REQ和局部Finding都可以成为ACL来源，一个ACL可以承接多个同根因或同验证路径的问题。

验证证据的适用范围由开发验证规范负责。计划版本不证明ACL已经交付；正式版本由产品版本总览（在采用项目中维护）选择实际纳入的REQ和Loop，并由Git标签固定。
