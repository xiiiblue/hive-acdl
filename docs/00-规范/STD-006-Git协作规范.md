# STD-006：ACDLGit协作规范

> 文档状态：Review
>
> 提取说明：由来源规范整理为通用草案；项目命令和目录按采用项目配置。
>
> 责任角色：Director
>
> 适用范围：活动工作树、提交、分支、Pull Request和正式Git标签
>
> 本文负责：规定提交怎样组织、何时使用分支和Pull Request，以及哪些历史不得改写

根`AGENTS.md`负责操作权限、已有修改和破坏性操作保护；本规范不重复这些要求。提交说明只概括变化并提供入口，不代替REQ、设计、Loop、环境、版本记录或Director确认。

## 1.工作树和暂存

修改前检查当前分支、工作树、暂存区和已有差异，区分当前任务与他人工作。暂存时只列出已确认路径，不使用`git add .`、`git add -A`或`git add --all`吸收未知差异。

Git写操作前重新核对工作树和暂存区。不得覆盖、回退、格式化、移动或删除无关修改。

## 2.一个最终提交只有一个目的

同一行为所需的代码、测试、迁移和文档可以放在一个提交中。以下情况拆分：

- 同一提交处理多个无关问题；
- 格式化、移动或重命名掩盖行为变化；
- 两项修改能够独立审查和回退。

拆分会形成不可用或难以理解的中间状态时保持同一提交。不得夹带调试输出、临时文件、生成垃圾或无关差异。本地和评审分支可以暂留试错提交，进入`main`前整理没有独立审查价值的内容。

## 3.提交说明

普通最终提交标题使用：

```text
<类型>(<范围>): <摘要>
```

类型使用：`feat`表示新增或改变产品能力，`fix`表示修复错误，`refactor`表示不改变外部行为的重构，`perf`表示性能优化，`test`表示单独调整测试，`docs`表示文档，`build`表示依赖或构建，`ci`表示持续集成，`chore`表示其它维护，`revert`表示撤销提交。范围可以省略，使用稳定应用、包或职责名称，不使用人名、任务序号、阶段或版本。

摘要默认使用中文，写出具体动作和对象，不写“更新代码”“修复问题”，也不声称尚未发生的评审、完成或发布结论。原因不能从差异看出，或涉及事务、迁移、安全、兼容和恢复时，在正文说明原因、行为变化、影响、未处理内容和恢复要求。

相关对象有助于检索时使用：

```text
Refs: ISSUE-000042 ACL-000084
```

`Refs:`只表示相关，不表示结束。`Closes #编号`只用于外部平台Issue。提交说明不得包含密码、Token、私钥、主密钥、连接串、Cookie、生产数据或个人敏感信息。

## 4.分支、worktree和Pull Request按需要使用

项目不强制每项修改都建分支或Pull Request。需要并行开发、风险隔离、远端复验或逐行讨论时使用；多个独立事项使用不同分支或worktree。

|修改类型|最低要求|
|---|---|
|局部维护、低风险界面调整|相关检查和清楚的结果；不强制分支、PR、REQ或ACL|
|普通代码与产品变化|固定候选并运行受影响范围的统一验证；按跨模块影响和方案取舍选择评审|
|业务授权、持久数据、迁移恢复、关键跨进程关系或正式交付|固定候选并独立评审；需要隔离时使用独立分支，优先使用PR|

在`main`上准备开展需要独立评审的工作时先创建分支。文字、按钮位置、菜单归属、局部样式及无行为变化的内部清理，不因“用户可以看到变化”自动升级为必需的独立评审。

独立评审由未参与本候选实现的另一位人员或另一独立Agent执行，记录评审者、固定提交或Git树、差异起点、发现和处理结果。作者自查或同一Agent换会话自查只能标为自查；另一个模型名称本身不能证明独立性。评审者只读，修改由写入者处理；修改后复核受影响部分，无法安排独立评审时保留未完成状态，不用自查代替。

### 4.1分支名称

已登记工作的分支使用`<工作类型>/<编号>-<主题>`，正式记录使用`acl`、`dfl`、`erl`、`issue`或`req`及六位编号，例如`acl/000100-branch-naming`。分支对应一轮完整工作，不对应记录中的单个清单项。

无需登记的普通维护允许使用`fix/<主题>`、`docs/<主题>`、`refactor/<主题>`、`test/<主题>`、`build/<主题>`、`ci/<主题>`或`chore/<主题>`。是否建分支与是否登记分别判断，不为取得分支名补造记录或使用`spike`冒充原型；分支名不能豁免需要REQ、ACL或确认的变化。所有分支的斜杠只分隔一次。

特殊分支只允许：

- `release/v<主版本>.<次版本>`；
- `spike/<主题>`；
- `backup/<YYYYMMDD>-<主题>`。

`main`保持原名。`<主题>`只用小写英文字母、数字和单个连字符，名称不超过80个字符，不以Harness或人名开头。历史分支不批量改名或删除；继续工作时从当前基线新建合规分支。

创建或切换后运行`npm run branch:check`。Pull Request检查源分支，`detached HEAD`允许验证。

Pull Request按模板概括目的、实际变化、验证和剩余问题；已有正式记录时链接，不为填模板补造对象。合入权限统一按根`AGENTS.md`判断，已有目标授权无需再为相同范围请求确认。

任何授权都不允许强制推送、改写共享历史、跳过分支保护或隐瞒失败检查。解决冲突后重跑受影响的检查。

### 4.2多Agent协作与交接

同一文件任一时刻只有一个写入者。独立任务优先使用不同工作树；同一任务共享工作树时，事先划定不重叠的文件范围，由一位负责人统一验证、提交和推送。固定候选验证或评审期间停止写入。交接保存当前提交、已有差异、剩余问题和下一步；远端串行接棒还要核对远端基线，发现变化先查明来源。

交接后不强制推送或改写历史；互不兼容的方案使用不同分支。只读意见由当前写入者落地，不能把意见当成交接。

## 5.保护main和正式标签

进入共享`main`的提交不得通过rebase、reset或强制推送改写；撤销使用`git revert`。正式版本、里程碑或长期证据标签不得移动、覆盖或复用，修正时建立新提交和新版本结论。

## 6.形成最终提交前

确认分支、工作树和暂存区符合预期；差异只有一个明确目的；提交说明真实且不含敏感信息；所需检查已经运行；失败、跳过和未验证事实已经记录。未完成的候选可以提交或推送以便交接，但不能据此声称验证通过；是否合入或交付按根`AGENTS.md`判断。
